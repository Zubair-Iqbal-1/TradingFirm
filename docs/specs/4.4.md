## Spec

Part 4.4 adds `POST /analyze/{ticker}?horizon=swing&entry=<optional>` to ai-agent: it reads the dossier from data-engine, the regime (and the macro brief, once one exists) from risk-shield and the account from `users.settings`, classifies the ticker's unlabelled headlines through 4.2's classifier, groups headlines into events by a new `eventKey`, computes the plan with 4.3's `compute_plan`, asks the model for a verdict **that contains no price level**, merges the two into `models.verdict.Verdict`, and stores it in `ai.verdicts` with the full dossier and the exact prompt inputs, plus one row per LLM call in a permanent cost ledger that also re-seeds the daily caps at startup. It must **not**: let the model supply, change or round any price, R or size; treat headline text as instructions; invent a target when plan math rejects (the rejection is passed through as a `wait`/`avoid` reason); spend on an LLM call it cannot store (no pool → 503 first); repair or partially accept a model answer — **with one named exception: length only, never content.** A verdict string over its cap (reasoning 2,000, a bullet 300, a flag 100) is cut at the cap with a WARNING and nothing else about it is touched; a wrong count, a bad enum, a non-string, a blank, or `go` without a plan still rejects the answer whole (`test_over_long_strings_are_trimmed_not_rejected`, against `test_answer_breaking_the_contract_is_rejected`); re-send a labelled headline; retry anything; write into `data_engine`, `risk` or Redis keys outside `tf:ai:`; make a live LLM call in any test or verification step; apply a prod migration or rebuild any prod service. **Acceptance:** the three twins green, 0 skipped, every failure-branch test below passing by name; a twin round trip on `tradingfirm_dev` with a stubbed provider shown as actual output (analyze → verdict row + ledger row → second call `cached: true` with the provider still at one call → a new high-relevance headline → third call pays again); the cap-seed proof (Redis DB 1 counter deleted, twin restarted, counter back from the ledger); `docker-compose.yml` per-block SHA-256 table for the 8 untouched blocks; and the migration, both prod rebuilds and the first live call listed as waiting for a go.

## Decisions

### Blockers

1. **2.4 is shipped** (X1). 4.4 is not blocked. But it is **short one thing** (X2): dossier news items need `id` and the stored `sentiment`. 4.4 adds them in data-engine: after `upsert_news`, `build_news` reads back `id, url, sentiment` for the kept URLs (`WHERE ticker = $1 AND url = ANY($2)`) and `NewsItem` becomes `id: int | None`, `sentiment: dict | None`. A read-back that raises is a DB error like any other in the dossier (503); no pool → `id: null`, and ai-agent then classifies without write-back. The dossier's own cache can hold labels up to 15/60 min stale; harmless, because ai-agent's 7-day digest cache answers those for free and re-writes them (4.2 decision 6b).
2. **Macro source: neither a stub nor a reorder.** The premise is half wrong (X6): 3.6a/b exist; only 4.6 is missing. 4.4 calls risk-shield `GET /market/health` (real regime today) and `GET /macro/brief` (404 today → `brief: null`). The day 4.6 ships and the flag goes on, briefs appear in the verdict prompt with **no 4.4 change**. `ai.verdicts.macro_brief_id` is `UUID NULL`, **no foreign key** (it would reach into `risk`). Both reads fail open: risk-shield down → `macro.status: "unavailable"`, the prompt says so, the verdict still runs. Why not 4.6 first: it needs a flag flip and an out-of-hours risk-shield deploy, and a verdict with a real regime and no brief is already useful. New setting `RISK_SHIELD_URL`; the twin hard-codes `http://risk-shield-dev:8003`.
3. **D16 is superseded and recorded** (X7). Plan §1's "Anthropic SDK usage" bullet does not apply: no `anthropic` package, no `messages.parse`, no adaptive thinking, no `fallbacks`. Structured output stays `response_format.json_schema` in the existing provider; the `claude-api` skill is read for prices and the cache minimum only.

### Schema / storage

4. **`eventKey` in the classifier answer.** A lowercase slug, `^[a-z0-9]+(-[a-z0-9]+){1,7}$`, ≤ 80 chars, ticker first, no source, no date (`nvda-q3-guidance-cut`). The prompt tells the model to give the same key to the same story inside the batch. **Across batches a model will not reliably re-invent the same slug**, so the request gains an optional `knownEventKeys` (≤ 40, each regex-checked): analyze passes the keys already on the ticker's labelled headlines, and the prompt says "reuse one of these if it is the same story". Assembly (`events.group`) groups by key and hands the verdict one line per event: `{eventKey, date (earliest), sources: n, relevance (max), sentiment (mean, 2 dp), category (of the most relevant), oneLine (of the most relevant)}`, at most 15 events, high relevance first. A label without a key (or a headline the classifier could not label) is its own event, keyed by its digest.
   - ai-agent requires `eventKey` from the model; a bad slug rejects the batch (4.2 decision 5 unchanged). A Redis digest entry **without** `eventKey` is a cache miss. Prod has none that matter (the six live-check entries were deleted); the build confirms with a read-only `SELECT count(*) … WHERE sentiment IS NOT NULL` and reports the number.
   - data-engine accepts `eventKey` as **optional but validated**, so the deploy order data-engine → ai-agent never 422s.
   - **Files touched by the contract change.** ai-agent: `classifier.py` (`SCHEMA`, `ITEM_LIMITS`, `validate_answer`, `user_prompt`), `prompts/headline_classify.md`, `main.py` (`ClassifyRequest.knownEventKeys`, `eventKey` on response items), `tests/test_classifier.py`, `tests/test_classify_endpoint.py`, `tests/test_prompts.py`, `tests/classify_live.py`. data-engine: `main.py` (`NewsSentimentRequest`, `SENTIMENT_EVENT_KEY_MAX`/regex), `dossier/models.py`, `dossier/assemble.py`, `db.py`, `tests/test_news_sentiment.py`, `tests/test_dossier.py`. Pins: `test_item_limits_pinned_to_spec` and `test_sentiment_contract_pinned_to_spec` both gain the key. risk-shield is untouched (it ignores extra keys, 4.2 W3).
5. **`ai.llm_calls`, the permanent ledger** *(approval B)*. One row per LLM request that reached the wire, whatever it answered, **and nothing else**: no `cached` column, no row for a cache-served analyze. "Cached or not" is the *prompt* cache, which is the two token columns. A verdict-cache hit is visible on the verdict instead: `ai.verdicts.served_count INT DEFAULT 0` and `last_served_at`, bumped by one `UPDATE` per hit. Columns: `id BIGSERIAL`, `called_at TIMESTAMPTZ`, `et_day DATE`, `user_id UUID NULL`, `ticker TEXT NULL`, `route TEXT` (`analyze` | `classify`), `label TEXT`, `model TEXT`, `tokens_in`, `tokens_out`, `tokens_reasoning`, `cache_read_tokens`, `cache_write_tokens` (INT NULL), `cost_usd NUMERIC(12,6) NULL` (NULL = the gateway reported none, never 0), `outcome TEXT` (`ok` | `rate_limited` | `unavailable` | `rejected` | `refused` | `bad_response` | `auth_failed`), `counters TEXT[]` (which caps the call counted against), `verdict_id UUID NULL`. Written by the **routes** (`ledger.record`), never the provider, which stays database-free. 4.2's classify route writes rows too. Redis stays the live counter. A ledger write that fails never fails a paid answer: ERROR, and `tf:ai:state:ledger_missed:{day}` is incremented so `/usage` can show the ledger is short.
6. **Caps seeded from the ledger at startup** *(approval 1)*. After the pool and Redis are up, for each counter: `n = count(*) WHERE et_day = today AND $counter = ANY(counters)` — no other filter, every row is a wire call. If `n >` the Redis value, the shortfall is added. **Max of the two, never a plain overwrite**, because either side can be the short one. **The keys are 4.1's and 4.2's own, written by their own rule** — a relative `INCRBY` / `INCRBYFLOAT`, then `EXPIRE key ttl NX`; never a `SET`, which drops the key's TTL so the `EXPIRE` would push the expiry forward:
   - `tf:ai:state:llm_calls:{YYYY-MM-DD}` — `EXPIRE 129600 NX`
   - `tf:ai:state:classifier_calls:{YYYY-MM-DD}` — `EXPIRE 129600 NX`
   - `tf:ai:state:cost_day:{YYYY-MM-DD}` and `tf:ai:state:cost_month:{YYYY-MM}` from `SUM(cost_usd)` — `EXPIRE 3456000 NX`

   The in-process `MemoryCap`s and `MemoryCost` are seeded too, always, so a Redis that dies later does not restart the day at zero. With Redis down the `MemoryCap`s are seeded instead. No pool at boot → no seed, one WARNING, `/health` gains `capsSeeded: false`. Runs once, before the app serves, so nothing races it.
7. **Migration is `007_ai.sql`**, not `005_ai.sql` (X4); plan correction in `docs/decisions.md`. `IF NOT EXISTS` throughout. Tables: `ai.verdicts` (plan §4 columns + `entry`, `thesis`, `thesis_breakers`, `risk_flags`, `plan_rejection JSONB NULL`, `prompt_inputs JSONB`, `prompt_sha TEXT`, `fingerprint TEXT`; `dossier JSONB` is the full document, `prompt_inputs` the exact projection the model saw — D5), `ai.verdict_outcomes` and `ai.judgments` as the plan lists them (unused until 4.5 / Phase 6; `position_id UUID`, no FK — `signals.positions` does not exist), `ai.llm_calls`, `users.settings (user_id UUID PK → users.profiles, account_size NUMERIC, risk_per_trade_pct NUMERIC, default_temperament TEXT)`. The dev user is seeded with `INSERT … ON CONFLICT DO NOTHING` — re-runnable, which is what the "no plain INSERT seeds" rule protects. **The seed is `account_size = NULL`, `risk_per_trade_pct = 1.0`** *(approval A)*: the repo is public and an account size never goes into a migration. Until it is set with the one SQL line in `docs/runbook.md`, `/analyze` answers 409. It never reaches the model either: the prompt carries the plan's levels and R, not the size or the risk budget. 001's four unused `ai.*` tables are left alone. ai-agent **reads** `users.settings`; no service owns `users` yet and nothing writes it until 5.3.

### `/analyze` behaviour

8. **Loopback only**, the port 4.2 already set; no token. **Verdict cache (D18):** Redis `tf:ai:verdict:{userId}:{TICKER}:{horizon}:{entry|auto}` → `{verdictId, fingerprint}`, value `{verdictId, fingerprint, entry}`, flat TTL **4 h** (ai-agent has no exchange calendar and does not get one for this). **`entry` omitted = `auto` = the dossier's last daily close, rounded half-up to cents** *(approval 2)*; the key says `auto`, and **the resolved number is stored in `ai.verdicts.entry` either way**, with `entry_source` = `given` | `last_close`. A given entry is keyed in integer cents. `?fresh=true` skips the cache and still pays under the caps. One normalizer, `tickers.normalize_ticker` + `validate_ticker` (upper, strip, 1–5 letters — data-engine's rule, copied and pinned by `test_ticker_rule_pinned_to_data_engine`); every key and every outgoing URL goes through it.
9. **Invalidation rule: the input fingerprint.** `sha256` of canonical JSON of: the sorted **high-relevance** event keys, the next earnings date, the regime (from the capped score), the macro brief id, the entry key (`auto` or cents), the last daily bar's date (`asOf`), account size, risk %, the verdict prompt's sha, the model id, and **the price bucket** *(approval 6)*: the dossier's current close, in whole ATRs from the **cached verdict's entry**, truncated toward zero — `int((close − cachedEntry) ÷ atr14)`. A move of ≥ 1 ATR either way since the verdict changes the bucket and forces a new one; 0.99 ATR does not (`test_price_move_of_one_atr_invalidates`). `asOf` catches a new day; the bucket catches a same-date partial bar that moved. For a new verdict the reference is its own entry. A cache entry is served only if its fingerprint equals the current one. So a new high-relevance headline, a moved earnings date, a regime change, a new bar, a ≥ 1 ATR price move, a new brief, a settings edit or a prompt edit each force a new verdict; medium/low headlines and a re-ordered news list do not. Cost of the check: a cache-served analyze still reads the dossier and risk-shield, and **can still pay one classifier call** (that is how a new headline is found), but never a verdict call.
10. **Classifier reuse: the function, not an HTTP call to itself** *(approval C)*. Analyze calls `classifier.classify()` in-process with only the items whose `sentiment` is null, then the same write-back loop, moved out of the route into `classifier.write_back()` so both routes share one code path. Labelled rows are never sent. **Expected calls per analyze:** classifier 0 or 1 (X3), verdict 0 or 1. First analyze of a ticker: 1 + 1. Repeat inside the TTL with unchanged inputs: 0 + 0. **Nobody else calls the classifier today** (X9), so 4.2's "~14 market batches a day" is not happening: the 40 cap is, for now, 40 first-time analyses a day, and it binds before the global 100 (2 global calls per fresh analyze → 50). Market headlines stay unlabelled until 4.6 decides who classifies them; if that becomes a loop, the 40 must be re-argued there. A classifier refusal (cap, cooldown, 429, bad batch) **fails open**: the verdict runs on unlabelled headlines, each its own event, and the response carries `newsClassified: false`.
11. **Headline text is untrusted input.** Four layers, in this order of importance:
    - **The LLM-facing schema has no price, R or size field** (derived from `Verdict`, strict, all fields required): `verdict`, `confidence`, `reasoning`, `thesis[3]`, `thesisBreakers`, `riskFlags`, `invalidation`, `holdThroughEarnings`, `horizonDays`. Every number in the stored plan comes from `PlanMath`. When plan math rejects, the schema's `verdict` enum is `["wait","avoid"]`, so `go` cannot come back. An injected headline can at worst tilt the text or the go/wait call; it cannot move a stop.
    - Untrusted text reaches the verdict prompt only as JSON string values (`json.dumps`), inside one block delimited by a per-request random nonce tag, so a headline can neither close the structure nor forge the delimiter. The system prompt states that everything inside the block is data and that instructions found there are to be reported as a `riskFlags` entry, not followed.
    - The verdict sees an event's `oneLine`, not the raw headline or summary; raw titles only for unlabelled items. All through `sanitize_untrusted` (control characters stripped, whitespace collapsed, 300 chars).
    - Tests: **`test_headline_cannot_break_out_of_data_block`** (a title carrying the closing tag, quotes, newlines and "ignore previous instructions" leaves the block intact and the system text unchanged) and **`test_injected_headline_cannot_change_levels`** (a stubbed answer that obeyed the injection still stores plan math's numbers).
12. **`cache_control`: gated, off by default, not measured yet — and I cannot measure it honestly before approval.** `prompts/verdict.md` does not exist (the spec is the only file written now), there is no offline Claude tokenizer, and the repo has no Anthropic key for `count_tokens`. What is known: the classifier file is 2,951 chars ≈ 740 tokens by itself; the 1,520 measured total includes schema and scaffolding whose position relative to a cache breakpoint is unknown (X10). **Classifier: no caching.** Verdict: the provider gains a keyword-only `cache_system: bool = False` that sends the system message as one text block with `cache_control: {"type": "ephemeral"}` (4.1's callers and tests unchanged); analyze passes `settings.llm_verdict_cache`, **default false**. The measurement is the live check (decision 14): call 1 runs with the flag on; **`cacheWrite > 0` is Anthropic's own statement that the prefix cleared 1,024**, and the report states the count. It stays on only if it cleared. The prompt is never padded to reach the bar. Economics, stated so the flag is not assumed to pay: 5-minute TTL, write 1.25×, read 0.1× — it pays only when analyses cluster (a session of several tickers, 4.8's five), and the ledger's two cache columns are what will show it.
13. **ATH `no_target` stays open.** Any `PlanRejected` is passed to the model as `plan: null, planRejection: {reason, detail}`; the verdict is `wait` or `avoid`, `riskFlags` gains `no plan: <reason>`, and `plan_rejection` is stored. No synthetic target.

## G1.5 — state

## Addition after the build, before the first push: `LLM_PROVIDER_ORDER` and the serving host

**As first added (`5c59bb0`), then changed before the push (this version is what ships):** the setting defaulted to empty and pinned with `allow_fallbacks: false`. That path is removed.

- **Default `LLM_PROVIDER_ORDER = "anthropic"`.** Every request carries `provider: {"order": [...], "allow_fallbacks": true}`; a comma-separated value becomes the list, in that order. **`allow_fallbacks` is always true — there is no setting and no code path that makes it false.** The order is a preference: a host that is down costs a cache miss, never a failed call. **The field is on every request, always: there is no opt-out.** An empty or malformed `LLM_PROVIDER_ORDER` is a config error and `Settings` refuses to construct, so the service does not start (the first version's explicit-empty opt-out was removed before the push). The provider parses the order again, so a value that somehow got past `Settings` still sends nothing and reserves nothing. Prod's compose line is `${LLM_PROVIDER_ORDER:-anthropic}`, which also turns an empty `.env` value into the default. No `.env` line is needed.
- **The host that actually served the call is recorded.** OpenRouter returns a top-level `provider` in the response body; it becomes `LLMResult.host` and **`ai.llm_calls.host TEXT NULL`** — added to `007_ai.sql` in place, since 007 is applied nowhere but `tradingfirm_dev` (rebuilt there: tables dropped, its `schema_migrations` row deleted, `dev-db.sh` re-applied, rerun a skip). NULL = not reported, and always NULL on a failed call.
- **A fallback is visible:** when a host is reported and its slug form (`"Google Vertex"` → `google-vertex`) is not `order[0]` (region suffix ignored), the provider logs one WARNING naming both. The call is still a success.
- **The twin is not protected by this setting**, and no test pretends it is: `test_provider_order_is_never_set_in_the_twin` is dropped. What keeps the twin off an LLM is the empty key, the two caps at 0 and the `.invalid` base URL (`test_twin_never_calls_openrouter`); the twin simply runs with the default order, which those locks never let reach the wire.
