## Spec

Part 4.2 gives `services/ai-agent` its first route: `POST /classify/headlines` takes up to 30 headlines, skips sending any it has already classified, sends the rest to the model as **one** structured call behind `prompts/headline_classify.md`, and writes **every** item that carries a row id back to `data_engine.news_items.sentiment` — cached or freshly classified — through a new data-engine route `POST /news/{id}/sentiment`. It also builds the service's first lifespan (Redis via `cache.create_redis` + one `httpx` client on `app.state`, bounded and fail-open), a **second, smaller daily cap** for the classifier so a batch loop cannot eat the analyst's budget, and a running USD cost total for today and this month readable at `GET /usage` without logging into OpenRouter. It must **not**: make a live LLM call in any test, script or verification step (the first live call is decision 14, after the user adds the key and says "go"); retry anything; repair, truncate or partially accept a model answer that breaks the item contract; let a write-back failure fail a classification already paid for; write into another service's Postgres schema or Redis namespace; apply a migration or rebuild/deploy any prod service.

**Acceptance:** all three twins green with 0 skipped and every failure-branch test below passing by name; a manual end-to-end run on the dev twins (`GET /news/market` for ids → `POST /classify/headlines` with a stubbed provider → row's `sentiment` populated → a second identical call writing the row again from cache with no LLM call) shown as actual output; `test_twin_never_calls_openrouter` extended to seven locks and `test_twin_never_writes_prod_data_engine` green; the byte-identical table for the **eight** unchanged compose blocks, each named; ai-agent coverage reported before and after against the 84 tests / 93% baseline, showing `cache.create_redis` now covered; and the prod rebuild, the port change and the first live call listed as waiting for a go, never performed.

## Decisions

1. **No Postgres pool in ai-agent.** 4.2 writes no `ai.*` table — the durable record is data-engine's, reached over HTTP. `database_url` stays unused and migration `005_ai.sql` stays in 4.4. (`config.py`'s "4.2 builds the pool" comment is corrected.)
2. **No `ratelimit.py`** (4.1 deferred the decision here). One batch is **one** LLM call, the route is caller-driven rather than a loop, and the wire is already bounded by two daily caps plus the post-refusal cooldown. An in-process sliding window prevents no failure those three do not. It earns its place when an unattended loop calls the provider — the watcher, or 4.5's nightly scorer. Recorded in `docs/decisions.md`.
3. **One call per batch, not per headline.** The schema returns an array; `index` ties each answer back to the prompt line.
4. **`oneLine`, not `one_line`.** The plan row wrote snake_case; every payload in this repo is camelCase. Recorded in `docs/decisions.md` as a plan correction.
5. **An answer that breaks the item contract rejects the whole batch** — 502, nothing cached, nothing written back. No repair, no re-ask, no partial accept.
6. **Write-back is fail-open and never blocks the response** — but see decision 6b, which is what stops fail-open from becoming permanent.
6b. **Every item with an id and a classification is written back, cached or fresh.** A cache hit costs no LLM call, so there is no reason to skip it, and skipping it opens a permanent hole: one write-back that 404s or times out would leave `sentiment` NULL while the 7-day digest keeps answering from cache, so 4.4's `sentiment IS NULL` filter would re-submit that headline forever for no result. Writing back on every call means **the next call heals the failed write** — that is the repair mechanism fail-open relies on.
7. **Error → HTTP mapping:** `LLMCapExceeded` / `LLMCooledDown` / `LLMRateLimited` / classifier cap → **429** (what `ai_agent_client` already expects, spec 3.6b decision 1); `LLMNotConfigured` / `LLMAuthFailed` → **503**; `LLMUnavailable` → **503**; `LLMRejected` / `LLMRefused` / `LLMBadResponse` / item-contract violation → **502**; a `ValueError` out of `validate_request` → **500**, because the classifier builds that request itself, so it is our bug and not the caller's (a caller's bad input is already a 422 from Pydantic, before anything is reserved). Details carry an error *type* and a count, never a body, a URL or the key (G14).
8. **`GET /news/market` items gain `id` and `sentiment`.** Additive and safe (W3, W14).
9. **`POST /news/{id}/sentiment` replaces the column wholesale**, it does not merge: a re-classification is the newer truth. 404 / 422 / 503 are data-engine's existing shapes.
10. **The item contract exists twice** — `classifier.ITEM_LIMITS` in ai-agent and the Pydantic model on data-engine's route — pinned by `test_item_limits_pinned_to_spec` and `test_sentiment_contract_pinned_to_spec`. Change both or neither; a drift is a 422 on every write-back.
11. **The twin gets two more locks:** `LLM_CLASSIFIER_DAILY_CALL_CAP="0"` and `DATA_ENGINE_URL=http://data-engine-dev:8001`. Seven in total, all asserted. Never drop them.
12. **The prompt file ships in the prod image** (`COPY . .`) and is read once at first use, not at import.
13. **`tests/classify_live.py`** joins the live-script list: manual only, guarded, 1 headline first then 5 (G2). Committed **unrun**.
14. **The first live call.** Nothing before this point touches OpenRouter. The order is: (a) you add one line `OPENROUTER_API_KEY=<key>` to `.env` — ai-agent checks it by non-emptiness only, never by prefix, and never prints it (G14); (b) you say "go"; (c) I rebuild and deploy prod `ai-agent` (G15 — ai-agent has no scheduler, so the XNYS timing rule does not bind it); (d) I run `tests/classify_live.py` with **one** headline, paste the answer + usage + cost, then **five**. Cost at Sonnet 5 list (W10): one headline ≈ 800 in / 400 out ≈ **$0.006**; five ≈ **$0.01**; a full 30-item batch ≈ 2,500 in / 2,000 out ≈ **$0.025**. The whole live check is **under $0.05**. This is also what proves the open 4.1 risk — `strict: true` structured output on the wire.
15. **Mock the transport of the client actually in use.** `respx` stays absent from `requirements-dev.txt`. Our own HTTP client (`data_engine_client`) is `httpx==0.28.1`, so its tests use **`httpx.MockTransport`**; the `openai` SDK runs on `httpx2`, so provider tests keep using **`httpx2.MockTransport`**. Both are the same rule — mock the transport of the client actually in use — and neither is `respx`, which patches `httpx` and cannot see the SDK. Written here so it is not re-litigated at 4.5.
16. **`writeBack` defaults to `true`.** The route's job is to leave the row classified; a caller that only wants an answer opts out explicitly.
17. **Prod `ai-agent` moves to a loopback-only host port.** See "Exposure" below.
19. **Redis does not persist reliably, and the cost totals and both caps are best-effort until it does** (W15). What survives what, precisely: the anonymous `/data` volume and its RDB snapshot survive a container **restart** and a `docker compose up -d` **recreate**, so a cap does not reset every time the container bounces. They do **not** survive `docker compose down` — the next `up` attaches a fresh anonymous volume and the old one is orphaned — and with AOF off and `save 3600 1`, an unclean kill can lose up to **an hour** of counter increments. Three things in this part lean on it: the month-to-date cost total, the 40-day daily history, and both daily caps. **No code in 4.2 changes this.** The fix — a declared named volume `redisdata:/data` plus `--appendonly yes` — goes to the housekeeping batch, and it is a prod change that needs its own go. Until then `/usage` figures are a floor, not an audit, and a `down`/`up` cycle resets the day's caps. This matters more from now on, because a real key sits behind those caps.
20. **Cross-source duplicates are not detected, and that is deliberate here.** The digest keys on URL, so the same event from Reuters, CNBC and Bloomberg is three digests, three classifications and three payments. Acceptable at this volume — it is already inside the ≤400/day estimate above. Where it actually bites is **4.4**: the verdict prompt would see three near-identical headlines as three events. The fix belongs to **dossier assembly**, not the classifier — dedup by event at the point where the prompt is built. No near-duplicate matching is built in 4.2. Recorded in `docs/decisions.md` as a known limitation.
18. **An expired digest means a paid re-classification** if a caller passes that headline again — intended, and accepted. The only thing preventing it is 4.4's `sentiment IS NULL` filter, and decision 6b is what makes that filter trustworthy: after 4.2 a successfully classified row is non-NULL, so 4.4 will not re-submit it once the digest expires. A caller that ignores the filter and re-posts an old headline pays for it; that is a caller bug, not a guard this part adds.

## The classifier cap: 40 calls per ET day

`LLM_CLASSIFIER_DAILY_CALL_CAP = 40`, separate from `llm_daily_call_cap = 100`.

| input | number |
|---|---|
| risk-shield's news poller | every 15 min, ~96 polls/day, heavily repeating (the digest absorbs the repeats) |
| unique market headlines reaching the classifier | **150–300 / day** |
| ticker headlines from analyst runs (4.4) | ~20 per ticker, a few tickers a day → **~100 / day** |
| total unique | **≤ 400 / day** |
| at 30 per batch | **~14 calls / day** |
| cap | **40** — about **3× headroom** over the expected load |
| left for the analyst, verdicts and the macro brief | **60 of the global 100** |

The classifier can therefore never consume more than 40% of the day's budget, and a runaway batch loop stops at 40 rather than at 100. Both numbers are env knobs; the twin hard-codes the classifier cap to `0`. The same line goes into `docs/decisions.md`.

## Exposure of the two new routes

`POST /classify/headlines` spends money and `GET /usage` reports spend, and a real key lands in `.env` immediately after this part. Today **every** compose service publishes on `0.0.0.0` (W13), so prod `ai-agent`'s `8004:8004` is reachable from anything on the LAN.

**4.2 changes prod `ai-agent`'s mapping to `127.0.0.1:8004:8004`.** After that:

- other services reach it by compose DNS (`http://ai-agent:8004`) — container-to-container traffic does not use the published port, so nothing breaks;
- the host can still `curl localhost:8004/usage`;
- nothing on the LAN can reach either route.

Neither route gets a shared secret in this part: loopback plus the compose network is the boundary, and the two daily caps are the second line of defence if that boundary is ever widened. A `X-TF-Token` in risk-shield's `WEEKEND_WRITE_TOKEN` shape is what to add **if** the route is ever called from off-host (Phase 5's notifier, or a public deployment) — noted here, not built.

The other nine published ports are **not** 4.2's work and are not touched. They belong in the housekeeping batch; I will raise them there rather than fold them in.

The same applies to Redis persistence (decision 19): the other nine published ports and `redisdata:/data` + `--appendonly yes` are two housekeeping items I will raise there, not fold in here.

## Keys and normalization (G1.5)

One function, `cache.headline_digest(title, url)`, built on the existing `canonical()`:

```
digest = sha256( canonical(url) if url.strip() else canonical(title) ).hexdigest()[:32]
```

Every lookup, every cache write and every in-batch dedup goes through it. Nothing else hashes a headline.

| key | contents | TTL | why |
|---|---|---|---|
| `tf:ai:classify:{digest}` | the classification JSON + `model` + `classifiedAt` | 604800 (7 d) | the "already classified" record. 7 days = data-engine's `NEWS_MARKET_MAX_HOURS` (168 h), so nothing the market-news window can return is ever re-sent |
| `tf:ai:state:classifier_calls:{YYYY-MM-DD}` | int, ET day | 129600 NX | the classifier's own cap — a *reservation counter*, not history |
| `tf:ai:state:llm_calls:{YYYY-MM-DD}` | int, ET day | 129600 NX | 4.1's global cap, unchanged |
| `tf:ai:state:cost_day:{YYYY-MM-DD}` | float USD, ET day | **3456000 NX (40 d)** | today's spend, and a month of day-by-day history for an admin panel to chart later |
| `tf:ai:state:cost_month:{YYYY-MM}` | float USD, ET month | 3456000 NX (40 d) | this month's spend |
| `tf:ai:state:cost_missing:{YYYY-MM-DD}` | int | **3456000 NX (40 d)** | calls whose answer carried no `cost`, kept as long as the day's total so a historical figure is never read without its caveat |

The three cost keys share one TTL; the two cap counters keep 36 h because they are reservations that must disappear, not history. `GET /usage` still returns **today and this month only** — no new route and no new response field in this part; the retained days are storage for later.

The durable record is **`news_items.sentiment`**: it survives forever and is what 4.4 filters on (`sentiment IS NULL`). Redis is the short-horizon guard that also serves a repeat caller an answer instead of a hole.

`cache.day_counter_key`, `reserve_call` and `release_call` gain a keyword-only `name=STATE_LLM_CALLS`, so the classifier counter reuses the exact same code path (W8). Existing positional callers and their tests are unchanged.

## The reservation rule (one rule, both tables)

**A classifier call is counted from the moment the request is sent, and the reservation is released on every refusal where no request reached the wire.**

| refusal | pre-wire? | reservation |
|---|---|---|
| bad request body (422, before anything) | — | never reserved |
| classifier cap reached (ours) | yes | **released** |
| `validate_request` ValueError (provider step 1) — **500**, our bug | yes | **released** |
| `LLMNotConfigured` / `LLMAuthFailed` (step 2 — no client is even built) | yes | **released** |
| `LLMCooledDown` (step 3) | yes | **released** |
| `LLMCapExceeded` (step 5) | yes | **released** |
| `LLMRateLimited` — this call got the 429 | **no** | kept |
| `LLMUnavailable` / `LLMRejected` / `LLMRefused` / `LLMBadResponse` | **no** | kept |

Without this, a missing key would silently burn the classifier's whole day at the first refusal. 4.1's global counter keeps its own semantics unchanged — the provider already releases at exactly one point, and that point is pre-wire too.

## Writes table (G1.5)

Ordered as they happen in one request.

| # | write | before / after success | state left if it fails after this point |
|---|---|---|---|
| 1 | `classifier_calls` INCR (+`EXPIRE … NX`) | **before** the LLM request | reserved; released on any pre-wire refusal per the rule above, kept once the request is sent |
| 2 | `classifier_calls` DECR | on a pre-wire refusal | n/a — no request went out |
| 3 | `llm_calls` INCR (4.1, inside the provider) | before the wire | 4.1's semantics, untouched |
| 4 | the LLM request | — | both counters counted; no cache, no write-back |
| 5 | `cost_day` / `cost_month` INCRBYFLOAT (or `cost_missing` INCR) | **after** a 200 | totals under-report by this call; WARNING; nothing else changes |
| 6 | `tf:ai:classify:{digest}` SET EX, per freshly classified item | after the batch validates | the item is re-classified on a repeat call (one more call); nothing wrong is stored |
| 7 | `POST /news/{id}/sentiment` → `news_items.sentiment`, **per item with an id, cached or fresh** | after #6 | the row stays unclassified and is counted in `writeBackErrors`; the answer is still returned and still cached, and the **next call rewrites it** (decision 6b) |
| 8 | (data-engine side) `UPDATE news_items SET sentiment = $2::jsonb WHERE id = $1` | one row | a raise leaves the row unchanged; the caller counts an error and a later call rewrites it |

Nothing is written when a request is refused at 422, 429 or 503. A request in which every item is cached performs #7 and nothing else.

## API

### ai-agent — `POST /classify/headlines`

Request (`extra="forbid"` throughout; 1–30 items):

```json
{"items": [{"id": 1234, "title": "…", "url": "https://…", "source": "Reuters",
            "publishedAt": "2026-09-20T13:02:00Z", "summary": "…", "ticker": "AAPL"}],
 "writeBack": true}
```

`id`, `url`, `source`, `publishedAt`, `summary`, `ticker` are optional; only `title` is required (non-blank, ≤1000 chars — data-engine's `NEWS_TITLE_MAX`). `summary` is trimmed to 300 chars **for the prompt only** — an input budget, not a truncated answer. Without an `id` an item is classified and cached but never written back. `writeBack` defaults to `true` (decision 16).

Response 200 — twelve items, all carrying ids, seven of them cache hits; **all twelve are written back**, one write fails:

```json
{"count": 12, "cached": 7, "classified": 5, "writtenBack": 11, "writeBackErrors": 1,
 "model": "anthropic/claude-sonnet-5",
 "usage": {"input": 812, "output": 410, "cost": 0.0057},
 "items": [{"id": 1234, "digest": "…", "relevance": "high", "sentiment": -0.4,
            "category": "guidance", "oneLine": "…", "cached": false}]}
```

`writtenBack + writeBackErrors` equals the number of items with an id, not `classified`. `usage` is `{}` when no call was made, and `model` is null. Item order matches the request.

### ai-agent — `GET /usage`

Unauthenticated, loopback/compose-network only, Redis-read, no LLM call:

```json
{"day": "2026-09-20", "month": "2026-09", "source": "redis",
 "calls": {"llmToday": 12, "classifierToday": 3, "costMissingToday": 0},
 "caps": {"llmDaily": 100, "classifierDaily": 40},
 "costUsd": {"today": 0.0412, "month": 0.9137},
 "cooldown": {"source": "openrouter", "secondsLeft": null, "cause": null}}
```

`GET /health` gains `redis`, `llmConfigured` (a bool — never the key, G14) and the two caps.

### data-engine — `POST /news/{id}/sentiment`
