## Spec

Part 4.5 adds a nightly scoring task to ai-agent's lifespan that, at 17:30 ET on every XNYS session, finds each stored verdict whose +1 / +5 / +20 **XNYS session** is closed, unscored and not expired, asks data-engine to refresh that ticker's bars (one ticker at a time, paced), reads the stored bars back — day 0's hourly bars that start at or after the ask, then the daily bars day0+1 … N — and writes one `ai.verdict_outcomes` row per horizon with return %, MAE %, MFE %, stop / target touched (judged on bar lows / highs against the stored plan), which touched first, the R at horizon and how many ask-session bars were used; plus `GET /journal/stats?days=90` with hit rate, mean return and avg R by verdict × horizon × model, and per-model confidence-bucket calibration. It must **not**: make any LLM call or import any provider, classifier or analyst code; call yfinance itself (only data-engine's existing refresh route does); let a bar that started before the ask into a window; score a horizon whose bars are not all present; score a ticker whose refresh did not complete with bars tonight, or treat a cooldown answer as fresh; score across a price-scale break; judge stop / target without a stored plan; score the same verdict + horizon twice; keep refreshing after a provider refusal or a second blank answer in one night; mix models in any rate; edit `007_ai.sql`; write outside the `ai` schema and the `tf:ai:` Redis namespace; apply a prod migration or rebuild any prod service. **Acceptance:** the three twins green, 0 skipped, every failure-branch test below passing by name; a twin round trip on `tradingfirm_dev` against `data-engine-dev` (fixture provider) shown as actual output — one seeded verdict asked mid-session with a plan and one asked after the close without one, `score_once` at a frozen clock → 3 + 3 rows with hand-checked numbers and `ask_session_bars`, a second run → 0 inserts and 0 refreshes, `GET /journal/stats` on `:8014`; the ai-agent image size before / after pandas + numpy; the `docker-compose.yml` per-block SHA-256 table; and migration 008 plus the ai-agent rebuild listed as waiting for a go.

## Decisions

### Where the day's bars come from — and how the scorer knows they exist

1. **A, approved: the scorer calls data-engine's existing `POST /stock/{t}/refresh` per due ticker.** No data-engine code change, no data-engine deploy. Plan §2's "0 external" is corrected in `docs/decisions.md` (supersedes that cell).
   - **Alpha Vantage, worst case.** A refresh makes at most one AV call (X3), and the night makes at most **20 refresh attempts, retries included** (decision 11) → **≤ 20 AV calls a night against the free tier's 25 a day** and 5 a minute. Realistic count is 0: AV is called only for a ticker yfinance has no validated past report date for. At 5 s spacing a burst can pass 5 / min; AV then refuses, data-engine starts its AV cooldown (`TTL_COOLDOWN_ALPHAVANTAGE = 3600`, `cache.py:55`) and every later refresh skips AV. **What the scorer sees while AV is on cooldown or capped: an ordinary 200 with bars**; the refusal lives in `earningsDates.reason` (`"cooldown"` / `"rate_limited"`), which the scorer ignores. It never stops the night.
   - **Refreshes 5 s apart are up to 12 a minute against AV's 5 a minute** *(approval)*. data-engine's own limiter absorbs that: every AV call waits on `alphavantage_limiter` (`ratelimit.py:76–78`, 5 per 60 s, `acquire()` blocks rather than refuses; `alphavantage_client.py:101`). A waiting refresh just takes longer (≤ 60 s, inside the 120 s timeout); the scorer never sees it.
   - **decisions.md, for 8.1:** at 8.1's volume (≈ 20 verdicts a day, each due at +1 / +5 / +20) due tickers reach ~60 a night against the cap of 20. Option C (a nightly bar job in data-engine) becomes necessary then; raise it at 8.1's G1.
2. **How the scorer knows the bars exist and are final**, three checks, all required:
   - **Time.** Slot **17:30 ET** on XNYS sessions only; no refresh starts after **18:10 ET**. Inside the CME halt, clear of risk-shield's 16:20 and 18:15+ downloads (X11).
   - **Written tonight, with bars.** Only a **200 with `dailyBars > 0` and `hourlyBars > 0`** counts: data-engine wrote the bars just now, and `ON CONFLICT DO UPDATE` replaced any partial bar a morning dossier stored (F4 shows one). **A 429 with `Retry-After` (the 15 min cooldown) is never fresh** (F1: it proves a completed refresh, which may have stored nothing): the ticker goes to the end of tonight's queue for **one** retry; a second cooldown 429 skips it for tonight and the night continues. A 200 with zero bars is a **blank answer** (F2), decision 11. A 429 without `Retry-After`, 502, 503, timeout or connect error stops the night. The 429 distinction is pinned on data-engine's side by `test_refresh_429s_distinguishable_for_ai_agent` (tests only).
   - **Present.** Daily: a bar dated exactly each XNYS session day0+1 … N. **A daily bar's date is data-engine's own rule** — `datetime.fromisoformat(ts).date()` with **no timezone conversion** (F4: `2026-09-18T00:00:00+00:00` → 2026-09-18), one function `sessions.bar_date`, pinned on that exact stored value. Hourly (only when day 0 is the ask session, decision 4): **no date function** — a 1h bar is in the window when `asked_at <= ts < close(day 0)`, compared as instants, with `close(day 0)` from the calendar (F4: `ts` is the start). The expected hourly starts are `open(day 0) + k h` for every one `< close(day 0)` and `>= asked_at`. **The hourly check is soft** *(approval)*: yfinance omits an hour in which nothing traded, and no trades means no touch, so a missing middle hour is not a data failure. **Expected > 0 and stored = 0 → defer** to the next slot (that does look like a data failure); otherwise score with the bars that exist, `ask_session_bars` records the count, and one WARNING names the missing start times. **The daily check stays hard**: a missing daily session → that horizon is not scored tonight (WARNING with ticker and date) and is tried at the next slot until it expires (decision 5).

### Trading days

3. **`exchange_calendars==4.13.2`, XNYS, the same pin as risk-shield**, is the counter; bar dates are the second check. G4 at build: `__version__` + a 3-line probe in the twin (sessions across 2026-11-26) before any code uses it. **Built lazily at first use with explicit bounds, `start=2026-01-01`, `end=today + 1 year`** (not the library's 20-year default), kept as a `tuple[date]` of sessions plus the open / close instants — no DataFrame in `app.state` (G8); never built at import. If the current date passes `end` in a long-running process, it is rebuilt once. The report gives the ai-agent image size before and after (pandas + numpy come with it).
4. **Day 0** *(change 2)*:
   - **Asked while a session is open** (`open(D) <= asked_at < close(D)`) → **day 0 = that session D.** The window starts with day 0's stored 1h bars that **start** at or after `asked_at` (decision 2's instant rule), then the daily bars day0+1 … N.
   - **Asked outside a session** (before the open, after the close, weekend, holiday) → day 0 = the last closed session; the window is daily bars only.
   - **+N = the Nth session after day 0**; the return is from session N's close.
   - `ask_session_bars` (008) = how many 1h bars were used: **0 is valid** — asked after the last hourly bar's start (15:30 ET; 12:30 on an early close, from the calendar). **NULL** = asked outside a session. The minutes between the ask and the next hourly start (≤ 59) are not observed; stated, not hidden.
   - The two AAPL verdicts (asked 2026-09-21 15:12 ET, a session): day 0 = **09-21**, +1 = **09-22**, +5 = **09-28**, +20 = **10-19**; `ask_session_bars` = 1 (the 15:30 bar).
5. **Due** = target session ≤ the latest closed session, unscored, and **not expired** *(change 3b)*: a horizon is no longer selected once its target session is **more than 10 sessions** before the latest closed session. Stats count it as `expired`, separate from `pending`. The selection query keeps a 60-calendar-day bound on `asked_at` as a cheap pre-filter (+20 + 10 sessions ≤ ~45 days).

### Scoring rules

6. All math in `Decimal`, bars through `Decimal(str(float))`, stored half-up to 3 dp. `entry` is `ai.verdicts.entry`. Long direction for every verdict. Over the whole window (ask-session 1h bars, then daily):
   - `return_pct` = (close of session N − entry) ÷ entry × 100.
   - `mae_pct` = (lowest low − entry) ÷ entry × 100; `mfe_pct` = (highest high − entry) ÷ entry × 100. Raw and signed.
7. **Stop / target, only with a stored plan that parses as `Plan`**; otherwise the four plan columns are NULL.
   - `stop_hit` = any window low ≤ `plan.stop` (a touch; D8's hourly-close rule is looser, so this over-counts stops — stated). `target_hit` = any window high ≥ `targets[0].price`.
   - `first_hit` walks the window **in order: day 0's 1h bars from the ask, then the daily bars**; the first bar touching either decides `stop`, `target`, or `same_bar` (stop first). NULL when neither.
   - `r_multiple`, 1R = entry − stop, stop always honoured, target not an exit: exit at the stop, or at that bar's open when the open is already at or below it; else session N's close.
   - A stored plan that does not parse: verdict not scored (ERROR), stays pending, expires under decision 5.
   
   **7b. Price-scale break** *(change 4, F3)*. Bars are split-adjusted and rewritten on each refresh, so a split inside the window puts entry 200 against bars at 50: −75 %, stop "hit", stored forever. **Guard: if the first window bar's open (the first 1h bar when `ask_session_bars > 0`, else the day0+1 daily bar) is more than 30 % from `entry`, the verdict is not scored** — ERROR naming the ticker, entry and that open; it stays pending and expires under decision 5. Cost: a real ≥ 30 % gap on the first bar (a biotech readout) is also left unscored; it shows as `expired`, not as a wrong number. **Dividend adjustment inside the window is accepted as small** (an ex-date re-scales earlier bars by the yield, ~0.1–1 %; the stored `entry` is not re-scaled).
8. **Scored once per horizon.** `INSERT … ON CONFLICT (verdict_id, horizon_days) DO NOTHING`; the selection skips scored pairs. Rows are never updated.
9. **Migration `008_journal.sql`**, `ALTER TABLE ai.verdict_outcomes ADD COLUMN IF NOT EXISTS`, all nullable:
   - `session_date DATE` — session N
   - `first_hit TEXT CHECK (first_hit IN ('stop','target','same_bar'))`
   - `r_multiple NUMERIC(8,3)`
   - **`ask_session_bars SMALLINT CHECK (ask_session_bars >= 0)`** — NULL = asked outside a session

   `007_ai.sql` is not edited; `test_migration_007_is_frozen` pins its SHA-256.

### Running it

10. **In ai-agent's lifespan, behind `JOURNAL_SCORING_ENABLED`** (code default `false`, prod compose `"true"`, the twin hard-codes `false`: `test_twin_never_scores_on_a_schedule`). One task after the pool and Redis steps, cancelled on shutdown, waiting only through a copy of risk-shield's `wallclock.py` (≤ 60 s chunks) with its tests and a header naming the source. No boot pass, no catch-up pass: a missed slot is caught by the next, since "due" needs no memory of past slots. Lock `tf:ai:lock:journal`, **`SET NX EX 2700`** *(change 8: the 40 min window 17:30–18:10 plus a last refresh's 120 s timeout plus margin)*; Redis down → no lock. Pool absent at the slot → slot skipped, WARNING. `/health` gains `journalScoringEnabled`, `journalLastRunAt`, `journalLastResult` (`{due, refreshed, scored, requeued, blank, expired, deferred, stoppedBy}`), in-process.
11. **Pacing and order (G6)** *(change 3)*:
    - One refresh per ticker per night; **≤ 20 refresh attempts a night, retries included**; 5 s between attempts; 120 s httpx timeout; none started after 18:10. Worst night: 20 × ~3 yfinance requests + ≤ 20 AV calls (decision 1).
    - **Order:** oldest due verdict first, **except tickers in the Redis set `tf:ai:journal:blanked`, which run last** *(approval, replaces v2's single `last_stopper`)*: **every ticker that blanked, plus any ticker that stopped a night**, is `SADD`ed with `EXPIRE 604800` (7 d, refreshed on each add), and read at the next slot. One remembered ticker would let three dead tickers rotate (A+B stop night 1, A+C night 2, A+B night 3 …) and starve everything else for 10 sessions; with the set, healthy tickers are always scored before the blanks can stop the run. A ticker leaves the set only by expiry. Redis down → plain order.
    - **Blank answer** (200 with `dailyBars == 0` or `hourlyBars == 0`) *(3a, rewritten per F2)*: that ticker is skipped and the night **continues**; a **second blank answer in the same night stops it.** Why two: F2 shows a delisted symbol and a yfinance rate limit give the same 200 + zeros; a delisted ticker blanks alone, a rate limit blanks every ticker. The first blank costs one refresh, a rate-limited night two.
    - **Stop the night:** 429 without `Retry-After`, 502, 503, timeout, connect error, or the second blank. The stopping ticker is added to `blanked`.
    - **Skip and continue:** the first blank; a cooldown 429 (requeued once, then skipped); a bars read that fails after a good refresh (DB-only, no IP at stake); a price-scale break; an unreadable plan.
    - Why nothing starves: a bad ticker blanks once, joins `blanked` and runs behind every healthy ticker from the next night on; every horizon expires 10 sessions after its target.
12. **No LLM anywhere.** `journal/` imports nothing from `providers`, `classifier`, `analyst`, `analyze` (`test_journal_never_imports_an_llm_path`, an `ast` walk); the round trip shows `ai.llm_calls` unchanged.

### `/journal/stats`

13. **`GET /journal/stats?days=90`**, `days` an int 1–365 (422 otherwise), the dev user's verdicts (`db.DEV_USER_ID`) asked in the last `days` days; read-only, one query, numbers from a pure `journal/stats.py`. Loopback = the existing `127.0.0.1:8004` publish, no route IP check (X10).
    - **Every group carries `model`** *(change 5)*: per `model` × verdict (`go` / `wait` / `avoid`) × horizon (1 / 5 / 20): `asked`, `scored`, `pending`, **`expired`**, `meanReturnPct`, `medianReturnPct`, `hitRate`, and over rows with a plan `withPlan`, `stopHitRate`, `targetHitRate`, `targetFirstRate`, `avgR`. **No rate or mean is ever computed across models** — 4.8 puts Sonnet and GLM verdicts on the same tickers into this table.
    - Hit: `go` → return > 0; `avoid` → return < 0; 0 is a miss; `wait` → `hitRate: null`.
    - **Calibration per model** and horizon, `go` and `avoid`: buckets `0–49`, `50–59`, `60–69`, `70–79`, `80–89`, `90–100` → `n`, `meanConfidence`, `hitRate`.
    - Rates 0–1 at 3 dp, `null` on a zero denominator, `n` beside every rate, nothing suppressed. Top level: `days`, `asOf`, `scoredThrough`. `pending` = due-to-come or due-and-unscored within 10 sessions; `expired` = decision 5 (the stats read uses `journal.sessions`).

## G1.5 — state

**Keys and normalization:** tickers through `tickers.normalize_ticker` + `validate_ticker` for every URL; daily bar dates through `sessions.bar_date` (data-engine's rule, no conversion); hourly bars compared as instants against `sessions.session_open` / `session_close`; sessions through `sessions.entry_session` / `nth_session`; outcome identity = 007's PK. Redis: `tf:ai:lock:journal`, `tf:ai:journal:blanked` (set).

**Run order:** slot → pool? → lock → select due (not expired) → group by ticker, oldest first, `blanked` last → per ticker, ≤ 20 attempts, until 18:10: refresh → classify the answer (ok / cooldown → requeue once / blank / stop) → bars read (1h for ask-session verdicts, 1d) → per verdict: parse plan → per due horizon: presence check → scale guard → score → one transaction per ticker → 5 s → status → unlock (blanked / stopping tickers `SADD`ed as they happen).
