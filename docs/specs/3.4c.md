# Spec — Part 3.4c: the weekend-exposure signal

Status: **v2, posted 2026-09-14, awaiting approval.** Base `b9b860a` (3.4b deployed, prod on `1e747bb8841e`). No file but this spec is written before the word "approved" (G1). v1's twelve decisions are settled below as chosen; v2 folds in your four changes and two smaller items, and corrects two things v1 got wrong (D5's early-close cut-off, and the staleness premise in Change 1 — see §Inputs at 15:30).

**Why the part exists (your framing, kept so the code is judged against it):** a weekend headline gap cannot be traded out of — stops fill at the gapped price, and by Sunday 18:00 ET the damage is priced in. The only useful moment is Friday afternoon, while the market is still open. The rule layered on top ("HIGH and in profit → flatten Friday, re-enter Monday") is yours, not the code's. **The system says how exposed this specific weekend looks and why. It never says trade.**

## Spec

Part 3.4c adds a `weekend` block to the Friday market rows from the close − 30 min onward and to every later Friday row, carrying a level — `LOW` / `ELEVATED` / `HIGH` — and the list of reasons that produced it, assembled from six inputs: the published (capped) score and regime with `overlay.base` recorded beside it, the VIX level and its 5-day direction, `econ_calendar` events falling between the Friday close and the Monday open, pending-decision language in the news window, and an operator-set "active situation" flag. The block rides in each row's `indicators` JSONB and on the health payload as one appended key; it changes no score, regime, trend or publish decision, it can never fail a publish, and a second read-only endpoint lines each Friday's last actionable level up against the following session's opening move so the levels can be judged after a few months.

It must **not**:
- add a `kind`, a slot, a scheduler cadence, a download, or an LLM call
- change a score, a regime, a trend, the throttle's publish decision, or any 3.3 scoring rule
- add a migration, a table or a column; the block lives in `indicators` and the log is computed from rows that already exist
- break `PAYLOAD_KEYS` append-only, or change 3.6a's inputs document in this part (D9)
- run in the twin beyond the round trip, add a compose flag, or change any compose service
- emit a trade action, a size, a stop, or the word "flatten" anywhere in the block or the endpoints
- put a non-null block on a non-Friday row, on any row before the cut-off, or on any row written before 3.4c
- let an unavailable calendar, an unreachable data-engine, a missing VIX, a Redis outage **or a non-finite number** fail, delay, skip or un-publish a check
- expose an unauthenticated write route (Change item: D2 ships with a shared secret now, not at going-public)
- touch prod except the G15 list

Acceptance:
- **Tests:** every failure-branch row names a passing test in `tf-risk-shield-dev`. The 691 existing tests pass, except those updated in place, each named with its reason in the report. The level table is pinned by `test_levels_pinned_to_spec`, the phrase list by `test_phrases_pinned_to_spec`.
- **Proofs required in the report** (Change: split): commit 2 proves every existing `econ_calendar.window()` caller is unchanged; commit 3a proves the live path is a no-op off-window.
- **Twin round trip:** synthetic Friday rows in `tradingfirm_dev` (one per level) served by `:8013/market/health`, `/market/indicators` and the log endpoint, then deleted; counts back to 0 and Redis DB 1 `tf:risk:*` back to 0.
- **Twin write path (added at approval, 2026-09-14):** a twin-only `WEEKEND_WRITE_TOKEN` is set for the round trip and one `PUT` + `DELETE` on the situation route is run end-to-end, then the token goes back to empty.
- **Prod after the go:** the first close − 30 min → 16:20 rows carry a block whose reasons match what the calendar and the news actually held that afternoon, checked by hand in chat.

## Inputs at 15:30 vs at the settle (Change 1)

**Your premise was half right, and the half that is wrong is in your favour.** Verified 2026-09-14 against live prod rows and the monitor code:

- `overlay.base` on a 15:30 row is **not** Thursday's settle score. It is *this check's* score, recomputed at 15:30 — but five of the six monitors read `align()` / `complete_bars`, which drop a partial bar, so those five score **Thursday's closes**. Only `vix` is live.
- `vix` takes `level = entry["close"][-1]` — the **last** bar, partial included — and its `prev` (the 1-day spike test) from the last *complete* bar. Prod rows from today show it: at 13:40–14:15 ET the vix raw carried `date 2026-09-14, partial true`, level walking 16.78 → 16.67, while `spy_trend` carried `date 2026-09-11`.
- So a Friday-afternoon level is **not** a Thursday-VIX level. It is a live VIX inside a Thursday-bars score, plus (Change 2) a cap from Friday's live futures.
- One caveat that stays: the quotes cache TTL is 300 s and equals the slot, so the live VIX refreshes every **10 minutes**, not 5 (open question 3 — visible above: 14:10 `fresh`, 14:15 `cached`, same 16.67). `vixAsOf` carries the view's own `asOf`, so a row never hides its true age.

| input | on a 15:30–15:55 row | on the 16:20 settle row |
|---|---|---|
| `cappedScore` / `regime` (the reason, Change 2) | this check's monitor score, capped by the ES=F/NQ=F move since **Thursday's** settle | the settle's own score; the overlay is exempt there, so `cappedScore == baseScore` |
| `baseScore` (recorded, not scored on) | same score before the cap | same as `cappedScore` |
| five monitors inside it | Thursday's complete closes | Thursday's complete closes until 16:15, Friday's complete bars at 16:20 |
| `vixLevel` | **Friday, live**, partial bar, ≤ 10 min old | Friday's settled 16:15 close, `vixPartial false` |
| `vix5dChangePct` / direction | complete closes only: Thursday vs the Thursday 5 sessions back | Friday vs 5 sessions back |
| calendar events | the same window both times (Friday close → Monday open) | same |
| news | ≤ 5 min old (D6 reuse), 24 h window | same |
| active situation | Redis, read every check | same |

`inputs` therefore carries **`baseScoreAsOf`** (the ET date of the complete bars the five monitors read) and **`vixAsOf`** (the view's `asOf`), plus `vixPartial` and `quotesSource` (`fresh` / `cached` / `last_known`), so a row states its own staleness instead of the reader having to know these rules.

## Decisions (settled)

### D1 — HIGH vs ELEVATED: **A**, with Change 2 applied

Reasons and weights (provisional like 3.3's and 3.4b's; D11's log is what retunes them):

| reason | fires when | weight |
|---|---|---|
| `regime_weak` | **`cappedScore`** ≤ 39 | 2 |
| `regime_soft` | **`cappedScore`** 40–59 | 1 |
| `vix_high` | VIX ≥ 25 | 2 |
| `vix_elevated` | VIX 20–24.99 | 1 |
| `vix_rising` | VIX up ≥ 15 % over 5 complete sessions | 1 |
| `scheduled_event` | a calendar event between Friday close and Monday open | 2 each, capped at 2 |
| `pending_decision` | ≥ 1 matched phrase in the news window | 1 (2 if ≥ 3 distinct items) |
| `active_situation` | the flag is set and unexpired | 2 |

**Level:** `HIGH` ≥ 4, `ELEVATED` 2–3, `LOW` 0–1. **Override:** `active_situation` alone is never HIGH; with any other reason it is.

**Change 2 — the regime reason reads the published (capped) score, not `overlay.base`.** The cap is never less cautious than the base, and a Friday intraday futures drop is exactly the thing a weekend read must not ignore; this keeps 3.4b's asymmetry (a cap lowers, never raises). `baseScore` and `cappedScore` both stay in `inputs`, and the block records which one the reason used (`regimeSource: "capped"`), so the log can be re-scored on the base later without re-deriving anything. On the settle row the two are equal by construction (the overlay exempts it).

### D2 — the active-situation flag: **A**, with a shared secret now

- `PUT /market/weekend/situation {"text": "…", "hours": 72}` and `DELETE /market/weekend/situation`. `GET` is part of `/health` and the block; there is no unauthenticated write.
- **Auth (your smaller item):** a shared secret in an `X-TF-Token` header, compared with `hmac.compare_digest` against `settings.weekend_write_token` (a `SecretStr` from `WEEKEND_WRITE_TOKEN`). **Empty token ⇒ the route answers 503 `disabled`** — it never falls open (F17). Prod compose gets the var; the twin hard-codes it empty, like every other twin override. The secret is never logged, never echoed in an error, and is checked by shape only in any report (G14). This is the service's first write endpoint, so the rule starts here rather than at going-public.
- `expiresAt` is mandatory, `hours` ≤ 168, and the Redis TTL is set from it, so a forgotten flag dies on its own. Cleared by DELETE, by expiry, or by a flush.
- `setBy` records the caller's token *id* only if we ever add more than one; for now it is the literal `"operator"`.

### D3 — the 16:20 settle row: **A, yes.** The settle's exemption from 3.4b's futures cap is about the cap, not the block; `overlay.base == cappedScore` there, and D11's move is measured from exactly that row.

### D4 — "Friday": **A.** The last XNYS session before a gap of ≥ 2 calendar days with no session (Friday normally, Thursday before a Friday holiday, Friday before a Monday holiday). Computed from the XNYS calendar already in `scheduler`. The block records `gapHours` (close → next open).

### D5 — the cut-off: **A, corrected.** **close − 30 minutes**, not v1's "90 minutes before an early close" — v1 was internally inconsistent (30 min on a normal day, 90 on a half day, for no reason). So:

- Normal session: rows at 15:30, 15:35, 15:40, 15:45, 15:50, 15:55, 16:00 (7 market) **+ the 16:20 settle** = 8.
- Early close 13:00 ET: 12:30 … 13:00 (7 market) + the settle = 8. Identical shape.
- **Your smaller item, verified 2026-09-14 in `tf-risk-shield-dev`, offline:** `slots_for_day` puts the settle at **16:20 ET on early-close days too** — `2026-11-27` (day after Thanksgiving) and `2026-12-24` both return 43 market slots ending `18:00 UTC` (13:00 ET) **and** a settle at `21:20 UTC` = 16:20 ET; `2026-09-11` returns 79 market slots and the settle at `20:20 UTC`. The settle slot is unconditional for any session day (`scheduler.slots_for_day`, `settle_time(day)`), so the named row exists on a half day: **the 16:20 ET settle, 3 h 20 min after a 13:00 close.** It is `kind: settle` and carries the block under D3.

### D6 — news: **A.** `macro_inputs.news_section` against data-engine's existing `/news/market`, `hours = 24`, `limit = 50` (inside the pinned 168 / 100 bounds), fetched once and reused from Redis for 300 s (W3) → ~2 fetches a Friday for 8 rows. `await`ed inside the check behind the existing 10 s timeout, inside a 5-minute slot; a failure is F3 and the block is still built. This is the check path's first HTTP call, and it is the only one.

**Phrases** live as a module-level tuple in `scoring/weekend.py`, pinned by `test_phrases_pinned_to_spec`, matched case-insensitively as regexes with word boundaries over `title + " " + summary`. Starting list: `expected to announce`, `deadline (sunday|saturday|this weekend)`, `talks (this |over the )?weekend`, `emergency (meeting|session|summit)`, `decision (is )?expected`, `vote (on )?(sunday|saturday)`, `ceasefire (deadline|talks)`, `tariff deadline`, `summit`, `ahead of monday`. The matched phrase and the item's title are recorded in the reason, so the block always shows *why* it fired.

### D7 — event source: **A.** `econ_calendar` gains a fourth type, `event`: free-text `title`/`detail`, allowed on any date including weekends. `EVENT_TYPES` grows by one; the duplicate rule becomes `(date, time, type)` so two situations can share a Sunday. `window()` and its body are unchanged — **commit 2 must prove that** (the `/market/calendar` tests, the news poller's coverage check and 3.6a's `calendar_section` all pass untouched, named in the report). CLAUDE.md's renewal step gains a line: the `event` rows are yours to add and prune; they are never required for the file to validate.

### D9 — the macro brief inputs: **A.** Not in this part. `health.weekend` is added later, together with whatever 4.6's prompt should do with it, so the inputs contract and the 16,000-byte budget stay untouched.

### D10 — the VIX 5-day direction: **A.** `compute_health` adds `health["vix5d"]` from the quotes view, mirroring 3.4b's `health["futures"] = futures_prices(view)`: a pure extract of the last 6 **complete** `^VIX` closes (so the direction is complete-bar arithmetic even while `vixLevel` is partial). No monitor changes, no scoring change; the night path never needs it. Direction measured over 5 complete sessions, not 5 calendar days.

### D11 — the outcome log: **A with the summary, and Change 3 applied**

`GET /market/weekend/log?weeks=26`, computed from `risk.health_checks`, no new storage.

- **Two levels per weekend (Change 3):**
  - `levelAtClose` — the last **market** row whose slot starts **strictly before** the session close (15:55 normally, 12:55 on a half day). This is the actionable one: at 16:00:0x the bell has already rung.
  - `levelAtSettle` — the 16:20 row's level, recorded for comparison.
- **The `summary` runs on `levelAtClose`**, per level: n, mean and worst `esMovePct`, so the question it answers is literally "did HIGH-at-15:55 predict a bad Monday".
- **The move stays settle → next open:** ES=F (and NQ=F) from the Friday **16:20 settle** row's stored `futures` to the **first row of the next session**. That 16:20 → 09:30 move is the gap proxy; SPY's own gap is not stored and storing it would be a new write.
- Row: `{closeDate, levelAtClose, levelAtSettle, points, reasons[codes], gapHours, esMovePct, nqMovePct, nextOpenScore, nextOpenRegime, status: "scored" | "pending" | "unscored"}`.
- A weekend where the two levels disagree is not an error; `summary` also reports how often they differ, because that is the first thing that will look suspicious.
